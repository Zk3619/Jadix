这是一个非常关键的技术决策阶段。既然你的目标是**“最大程度掌握代码”**且**“不复用高层框架”**，你需要的是**“库 (Libraries)"**而不是**“框架 (Frameworks)"**。

你需要像搭乐高一样，选择最底层、最灵活、文档最全的 Crates 来构建自己的引擎。以下是针对构建**现代风格 (Shadcn/MD3)** 原生 UI 引擎的底层原语深度对比与选型建议。

---

### 1. 窗口与事件循环 (Windowing & Event Loop)

这是应用的入口，负责创建操作系统窗口并分发输入事件。

| Crate        | 状态 | 优点                                                         | 缺点                                                     | 推荐度 |
| :----------- | :--- | :----------------------------------------------------------- | :------------------------------------------------------- | :----- |
| **`winit`**  | 成熟 | **行业标准**。跨平台支持最好 (Win/macOS/Linux/Android/iOS)。API 稳定，社区庞大。 | API 较为底层，需要自己处理事件循环逻辑。                 | ⭐⭐⭐⭐⭐  |
| **`tao`**    | 活跃 | Tauri 维护的 `winit` 分支。对 WebView 集成更好，修复了一些 `winit` 的 bug。 | 文档略少于 `winit`，本质是 fork。                        | ⭐⭐⭐⭐   |
| **`sdl2`**   | 成熟 | 游戏开发标准。输入处理非常强大。                             | 偏向游戏，UI 事件（如 IME、焦点）支持不如 `winit` 细致。 | ⭐⭐     |
| **`glutin`** | 维护 | 专注于 OpenGL 上下文管理。                                   | 现代 GUI 倾向于 Vulkan/Metal (wgpu)，它略显过时。        | ⭐      |

**🏆 最终选择：`winit`**
*   **理由**: 它是 Rust GUI 生态的基石。Iced, Slint, Dioxus 底层都用它。文档最全，遇到坑最容易找到解决方案。
*   **注意**: 配合 `accesskit_winit` 使用，以原生支持无障碍功能。

### 2. 图形渲染 (Graphics Rendering)

这是实现 Shadcn 风格（圆角、阴影、模糊、动画）的核心。你需要 GPU 加速。

| Crate           | 状态 | 优点                                                         | 缺点                                                         | 推荐度 |
| :-------------- | :--- | :----------------------------------------------------------- | :----------------------------------------------------------- | :----- |
| **`wgpu`**      | 成熟 | **WebGPU 标准的 Rust 实现**。跨后端 (Vulkan/Metal/DX12/GL)。WGSL 着色语言强大，适合写圆角/阴影 Shader。 | 学习曲线陡峭。需要自己管理 Pipeline, Buffer, BindGroup。     | ⭐⭐⭐⭐⭐  |
| **`skia-safe`** | 成熟 | Google Skia (Chrome/Flutter 核心) 的绑定。功能极其强大，自带文本/路径/滤镜。 | **C++ 依赖**，编译慢，体积大。更像“黑盒引擎”，不符合“掌控代码”的目标。 | ⭐⭐     |
| **`tiny-skia`** | 活跃 | 纯 Rust CPU 光栅化。API 简单。                               | **CPU 渲染**，复杂阴影/模糊会掉帧，不适合现代动效 UI。       | ⭐⭐     |
| **`glow`**      | 维护 | 轻量级 OpenGL 封装。                                         | OpenGL 已逐渐被淘汰 (macOS 不支持新版)，WGSL 更现代。        | ⭐⭐     |

**🏆 最终选择：`wgpu`**
*   **理由**: 只有 `wgpu` 能让你完全控制像素。你可以编写自定义 WGSL Shader 来实现 Shadcn 的 `box-shadow` 和 `border-radius`，而无需依赖重型引擎。
*   **关键**: 你需要自己实现 **Batching (批处理)** 来优化 Draw Calls。

### 3. 布局引擎 (Layout Engine)

实现 Flexbox/Grid 布局，不要自己写算法，这是数学深坑。

| Crate               | 状态 | 优点                                                         | 缺点                                       | 推荐度 |
| :------------------ | :--- | :----------------------------------------------------------- | :----------------------------------------- | :----- |
| **`taffy`**         | 活跃 | **Facebook Yoga 的 Rust 移植**。Flexbox/Grid 算法标准实现。性能极高。 | API 偏向函数式，需要适配到你的节点树结构。 | ⭐⭐⭐⭐⭐  |
| **`stretch`**       | 归档 | Yoga 的早期 Rust 移植。                                      | 已停止维护，不要用。                       | ❌      |
| **`cosmic-layout`** | 实验 | System76 开发。更贴合桌面环境。                              | 生态较小，文档不如 `taffy`。               | ⭐⭐⭐    |

**🏆 最终选择：`taffy`**
*   **理由**: 它是目前 Rust 生态中唯一成熟的 Flexbox 实现。你只需要负责将你的 UI 树节点映射到 `taffy::NodeId`，计算完布局后取回 `x, y, width, height` 即可。

---

### 4. 文本渲染 (Text Rendering)

原生 UI 最难的环节之一（字体加载、Shaping、Emoji、HiDPI）。

| Crate             | 状态 | 优点                                                         | 缺点                                             | 推荐度 |
| :---------------- | :--- | :----------------------------------------------------------- | :----------------------------------------------- | :----- |
| **`cosmic-text`** | 活跃 | **目前最强**。整合了 `rustybuzz` (Shaping) 和 `fontdb`。支持多字体回退、Emoji。 | 主要是 CPU 光栅化，需要配合 GPU 上传纹理。       | ⭐⭐⭐⭐⭐  |
| **`glyphon`**     | 活跃 | **`wgpu` + `cosmic-text` 的整合器**。直接将文本渲染为 GPU 图元。 | 封装了一层，但极大简化了 `wgpu` 集成。           | ⭐⭐⭐⭐⭐  |
| **`fontdue`**     | 维护 | 简单快速的字体光栅化。                                       | 功能较基础，复杂文本排版支持不如 `cosmic-text`。 | ⭐⭐     |
| **`rustybuzz`**   | 活跃 | 纯文本 Shaping 引擎。                                        | 只负责计算字形位置，不负责渲染。                 | ⭐⭐⭐    |

**🏆 最终选择：`glyphon` (基于 `cosmic-text`)**
*   **理由**: 虽然你想掌控代码，但文本渲染太复杂。`glyphon` 允许你直接将其集成到 `wgpu` 的渲染流程中，既保留了控制权（你可以修改 Shader），又避免了重写文本排版引擎。

### 5. 无障碍与输入法 (Accessibility & IME)

如果要达到商业级质量，这部分不可或缺。

| Crate                 | 状态 | 作用                                                 | 推荐度                            |
| :-------------------- | :--- | :--------------------------------------------------- | :-------------------------------- |
| **`accesskit`**       | 活跃 | **无障碍标准**。将 UI 树转换为 OS 可识别的无障碍树。 | ⭐⭐⭐⭐⭐                             |
| **`accesskit_winit`** | 活跃 | 将 `accesskit` 集成到 `winit` 事件循环。             | ⭐⭐⭐⭐⭐                             |
| **`ime`**             | 实验 | 输入法编辑器支持。                                   | ⭐⭐⭐ (通常 `winit` 内置了基础支持) |

**🏆 最终选择：`accesskit_winit`**
*   **理由**: 忽略无障碍会导致你的应用无法被屏幕阅读器使用。`accesskit` 正在成为 Rust GUI 的标准。

### 6. 颜色与数学 (Utilities)

| Crate         | 作用                                                         | 推荐度 |
| :------------ | :----------------------------------------------------------- | :----- |
| **`palette`** | 类型安全的颜色处理 (转换 RGB/HSL/OKLCH)。Shadcn 依赖 OKLCH 色域。 | ⭐⭐⭐⭐⭐  |
| **`glam`**    | 高性能数学库 (向量、矩阵)。`wgpu` 常用搭档。                 | ⭐⭐⭐⭐⭐  |
| **`euclid`**  | 2D 几何库 (Point, Rect, Size)。适合 UI 布局计算。            | ⭐⭐⭐⭐   |

**🏆 最终选择：`palette` + `euclid`**
*   **理由**: `palette` 对 OKLCH 的支持对于实现 MD3/Shadcn 的动态取色至关重要。`euclid` 的 `Rect` 和 `Point` 语义比 `glam` 更适合 UI 布局。

### 7. 推荐的技术栈组合 (The "Engine Starter Pack")

基于以上分析，这是为你定制的**“完全掌控”**技术栈：

```toml
[dependencies]
# 窗口与事件
winit = "0.30"
accesskit_winit = "0.20"

# 图形渲染
wgpu = "22"
glyphon = "0.7"  # 文本渲染 (基于 cosmic-text + wgpu)

# 布局
taffy = "0.6"

# 工具
palette = "0.7"   # 颜色空间 (OKLCH)
euclid = "0.22"   # 2D 几何
pollster = "0.3"  # 用于阻塞等待 wgpu 初始化
```

### 8. 架构集成示意图

你需要自己编写胶水代码将这些库串联起来。以下是数据流设计：

```text
[用户代码] (定义 UI 树)
      ↓
[你的引擎核心] (自研 Signal + 组件系统)
      ↓
[布局阶段] (taffy)
   输入：Style (Flex, Padding...)
   输出：Layout (x, y, w, h)
      ↓
[渲染准备] (Batching)
   将具有相同 Shader 参数的节点合并
      ↓
[GPU 提交] (wgpu + glyphon)
   1. 更新 Uniforms (颜色、分辨率)
   2. 绘制背景/边框 (自定义 WGSL Shader)
   3. 绘制文本 (glyphon)
      ↓
[窗口呈现] (winit)
```

### 9. 关键挑战与应对策略

1.  **圆角与边框的 Shader 实现**:
    *   **挑战**: `wgpu` 默认只画三角形。
    *   **策略**: 编写一个 `rounded_rect.wgsl`。在 Fragment Shader 中，根据 `uv` 坐标和 `border_radius` 计算 `distance`。如果 `distance < radius` 则绘制，否则 discard。边框可以通过绘制两个不同半径的圆角矩形叠加实现。

2.  **阴影 (Box Shadow)**:
    *   **挑战**: 实时高斯模糊很贵。
    *   **策略**: 
        *   方案 A (高质量): 使用 `wgpu` 的 Compute Shader 进行模糊 Pass。
        *   方案 B (高性能): 预生成阴影纹理 (9-slice patch)，或者在 Shader 中使用软阴影近似算法。

3.  **HiDPI 适配**:
    *   **挑战**: 4K 屏下字体模糊或 UI 过小。
    *   **策略**: 从 `winit` 获取 `scale_factor`。所有布局计算 (taffy) 和 渲染尺寸 (wgpu) 都必须乘以 `scale_factor`。`glyphon` 会自动处理字体缩放，但你需要配置好 `Resolution`。

4.  **状态重绘优化**:
    *   **挑战**: 每次鼠标移动都重绘全屏会发热。
    *   **策略**: 实现 **Dirty Rect 追踪**。当 Signal 变化时，记录受影响的节点区域。`winit` 支持 `request_redraw`，`wgpu` 支持只渲染特定区域 (Scissor Test)。

### 10. 总结

选择这套栈 (`winit` + `wgpu` + `taffy` + `glyphon`)，你实际上是在**构建一个简化版的 Flutter 或 Web 浏览器渲染引擎**。

*   **优点**: 代码 100% 可控，无黑盒，性能上限极高，完全定制 Shadcn 风格。
*   **代价**: 前 3 个月你可能都在和 `wgpu` 的 Pipeline 配置以及 `taffy` 的节点映射做斗争，而不是写 UI 组件。

**建议起步步骤**:
1.  先用 `winit` + `wgpu` 画出一个**带圆角的彩色矩形**。
2.  接入 `taffy`，让两个矩形能自动排列 (Flex Row)。
3.  接入 `glyphon`，在矩形里写上文字。
4.  最后再开始设计你的 Signal 系统和组件 API。

祝你好运，这将是 Rust 图形编程的一次绝佳实践！
